# 实施计划指导

## 目标

把计划写成下一位开发者可以直接执行的工程说明，而不是对用户需求的改写。计划必须说明现状、决策、具体改动位置、执行顺序、验证方式和范围边界。

## 工作边界

- 计划阶段只进行只读调研，不修改业务代码、配置、依赖或外部状态。
- 默认创建或更新计划文件；这属于计划交付，不属于实施。除非用户明确要求在对话中展示，否则不要把计划正文输出到对话。
- 不因任务复杂就自行进入计划阶段，除非用户明确表达计划意图，或仓库规则要求该类任务先提交计划。
- 用户同时要求“先计划，再实现”时，先交付计划并等待确认；不要在同一轮越过确认门禁开始实施。
- 遇到信息缺口时，先从仓库、需求文档和可用知识库中查证。只有不同答案会显著改变方案且无法查证时，才提出阻塞问题。

## 调研流程

1. 读取目标目录最近的 `AGENTS.md`、项目说明、包管理与构建配置。
2. 定位需求涉及的入口、核心模块、类型、接口、路由、状态管理、样式和测试；检查依赖、脚本、配置和现有用例，确认项目是否具备接口 Mock 与单元测试条件。
3. 查找同类实现，优先沿用项目已有模式；记录关键文件路径和必要的符号名。
4. 核对外部需求、接口文档或原型。按项目规则使用指定工具读取受管文档。
5. 识别约束、依赖、未知项、风险和明确不做的范围。
6. 基于调研结果选择最直接的实现路径，不在计划中罗列没有取舍结论的方案菜单。

调研应与任务规模匹配。局部修复只需定位相关链路；跨模块或架构改动要覆盖上下游契约、迁移和回滚影响。

## 计划质量要求

计划中的每个实施步骤都应回答：

- 改哪里：给出仓库相对路径；已知时补充组件、函数、类型或配置项名称。
- 为什么改：说明该位置在现有链路中的职责，以及选择该方案的依据。
- 怎么改：描述关键数据流、接口契约、状态变化、错误处理和兼容策略。
- 如何验收：给出可执行命令、测试范围或可观察行为。

同时遵守以下规则：

- 区分已确认事实、合理推断和待确认事项，不把猜测写成既定事实。
- 待办项使用 Markdown checkbox，按依赖顺序排列，每项保持单一、可验证的目标。
- 不写“修改相关文件”“完善逻辑”“注意兼容性”这类无法执行的空泛描述。
- 不预先规定尚未调研的文件名、API 字段或技术选型。
- 小改动保持精简；只有存在真实依赖、风险或阶段边界时才展开章节。
- 涉及 UI 时说明结构、状态、交互和项目视觉规范来源；不要在计划中凭空设计新体系。
- 验证优先覆盖本次改动相关的单元测试和类型检查；只有风险需要时才加入构建、端到端或浏览器验收。

## 完整需求专项检查

当任务要交付一条可独立验收的完整业务链路，通常涉及接口、页面、状态或多个模块时，在计划中明确体现以下判断。不要仅因为需求规模大就默认引入新的基础设施。

### 接口 Mock

- 需求依赖接口时，检查项目是否已有 Mock 框架、Mock 目录、环境开关、请求拦截或等价机制，并确认能否沿用现有模式。
- 项目具备 Mock 条件时，把 Mock 纳入实施步骤和待办，覆盖可运行的正常数据、关键边界和必要错误态，使真实接口未就绪时也能验证主要业务链路。
- Mock 响应必须遵循项目现有接口与拦截器契约，不得让业务组件为 Mock 编写专用分支。
- 项目不具备 Mock 条件时，在计划中说明判断依据；除非搭建 Mock 是需求的一部分或投入合理，否则不要擅自扩展范围。

### 单元测试

- 检查项目是否已有测试运行器、测试脚本、配置、测试工具和可参考用例，而不是只看是否存在 `tests` 目录。
- 项目具备单元测试条件时，把本次需求相关的单元测试作为主要自验收方式，写入实施步骤、正文末尾的 TODO 和验证顺序；明确测试对象、关键行为、边界或异常分支以及实际执行命令。
- 类型检查、构建、端到端测试和浏览器检查按风险补充，不能用纯人工验收替代本可由单元测试稳定覆盖的逻辑。
- 项目不具备单元测试条件时，记录现状并给出与项目能力匹配的替代验证方式；不要在没有成本与范围判断的情况下顺带搭建整套测试体系。

## 输出格式

默认使用下面的结构。计划较小时可合并实施章节，但不要省略需求理解、实施步骤、验证和非目标。

````markdown
---
name: <简洁中文标题>
overview: <一到两句话概括目标、关键方案与交付结果>
isProject: false
---

# <标题>实现计划

## 需求理解

- **目标**：<最终要解决的问题>
- **现状**：<从仓库调研得到的当前链路>
- **约束**：<项目规范、兼容要求、外部依赖>
- **方案**：<选择后的实现路径及理由>

```mermaid
flowchart LR
  A[现有入口] --> B[本次改动]
  B --> C[下游结果]
```

## 一、<实施阶段>

涉及文件：[`path/to/file.ts`](path/to/file.ts)

1. <具体改动及其原因>
2. <数据流、契约、状态或异常处理>

## 二、<后续实施阶段>

...

## 完整需求专项检查

- **接口 Mock**：<现有条件与依据；适用时说明 Mock 接入位置、数据场景和契约>
- **单元测试**：<现有条件与依据；适用时说明测试对象、关键用例和执行命令，并作为主要自验收方式>

## 验证顺序

1. `<相关测试或类型检查命令>`
2. <关键成功路径>
3. <边界、失败或兼容场景>

## 明确不做

- <本次范围外事项及边界原因>

## 待确认项

- <仅保留无法通过调研消除、且会影响实施的事项；没有则删除本节>

## 实施跟踪规则

- 实施过程中以本文末尾 TODO 为进度依据。
- 开始任务前先读取 TODO；每完成一个可独立验收的交付项并通过相关验证后，立即将对应的 `- [ ]` 更新为 `- [x]`。
- 不要等全部开发结束后一次性勾选，不得在缺少验证结果时提前勾选。
- 遇到阻塞时保持未勾选，并在该项后补充阻塞原因。
- 新发现的必要工作应补充为新的 checkbox，不得删除未完成事项。

## TODO

- [ ] <可验证的交付项>
````

`mermaid` 仅在三个及以上节点的数据流、依赖或状态变化能显著提升理解时保留。不要为了形式完整强行画图。

## 文件交付

- 默认将计划写入项目根目录下的 `docs/plans/`；目录不存在时创建该目录，不要写入 `.cursor` 或其他工具私有目录。
- 用户没有指定交付方式时，不在对话中输出计划正文；回复只说明计划已生成，并提供计划文件路径。
- 只有用户明确要求“直接输出”“在对话中展示”“不要创建文件”或指定其他交付位置时，才按其要求覆盖默认文件交付方式。
- 文件名使用 `docs/plans/<中文标题>_<8位短标识>.plan.md`；短标识只需保证当前目录内不冲突。
- 文件内链接优先使用仓库相对路径，引用仓库外材料时使用绝对路径或原始 URL。
- 每份计划必须保留“实施跟踪规则”，要求后续实施 Agent 在完成并验证每个交付项后立即更新同一计划文件中的 TODO checkbox。
- TODO 必须放在正文最下面；新计划的待办默认使用未勾选 checkbox。只有在更新既有计划且有实际完成证据时才勾选。

## 交付前检查

- 已完成与任务规模匹配的只读调研，计划引用的路径真实存在或明确标为拟新增。
- 方案已做出取舍，实施步骤按依赖排序且能落到具体代码位置。
- 计划已包含实施跟踪规则，明确要求后续实施 Agent 按完成和验证结果即时更新 TODO。
- 正文末尾 TODO 中的待办与实施阶段一致，勾选状态没有虚报。
- 完整需求已检查接口 Mock 和单元测试条件；具备单测基础时，计划已将相关单元测试作为主要自验收方式。
- 已覆盖成功路径、关键异常、测试或类型检查以及范围外事项。
- 没有实施代码，也没有把计划写成大段需求复述。
- 未收到特殊交付要求时，计划已写入项目根目录的 `docs/plans/`，且对话中未重复输出计划正文。
